# 划词图标浮现前先验证选区证据

ADR 0002 把触发一元化为划词图标后，macOS 端的手势检测（拖动超过阈值 / 双击抬起）只看手势形状，存在已知假阳性：双击空白、空白处拖动、拖窗口/拖文件都会浮出图标（Issue #2）。0002 原设想的补救「AX 命中测试过滤非文本位置」经实测否决：WhatsApp 的聊天区在 AX 里是一整块扁平 AXGroup（落点探不到文字），Finder 的文件名反而是 AXTextField（拖文件会被误判成选文字），两头都不成立。

改为手势结束后、浮现图标前，在串行后台队列上向 AX 索取「选区证词」，按三态处置：

| 焦点元素的证词 | 判定 | 处置 |
|---|---|---|
| 非空选中文字 | 有选区 | 浮现 |
| 选区为空（success 空串 / noValue） | 无选区 | 看剪贴板信号，否则丢弃 |
| 不支持选中文字，且前台是 Finder 或焦点是集合类角色（AXOutline/AXTable/AXList/AXBrowser/行/列/单元格） | 无选区 | 同上——桌面双击、框选、拖文件是在摆弄条目，不是选文字 |
| 不支持选中文字，且焦点是不透明容器（如 WhatsApp 的 AXGroup） | 无法作证 | 疑罪从无，浮现 |
| 焦点探不到（无障碍树未启用 / 查询失败） | 无法作证 | 注入激活开关后复判（见下），仍无法作证则浮现 |

辅助信号与机制：

- **剪贴板信号**：手势期间（mouseDown 快照 changeCount，mouseUp 比对，0.3 秒后再看一眼）剪贴板变过 → 视同有选区。覆盖「选中即复制」、没有 AX 选区的应用（如 Claude Code 的 TUI）——与 SelectionCapture 剪贴板新鲜度兜底服务的是同一批应用。
- **0.3 秒复判**：首判「无选区」不是终审——复查剪贴板之外还要重新问一次 AX，只认「有选区」的改判。因为迟到的证据真实存在：Terminal.app 连选区本身都是 mouseUp 之后才异步提交（实测注入手势：双击 +50ms 选区才可读，拖选 +5ms 可读但仍晚于紧随 mouseUp 的首判；备忘录等则在拖动过程中实时更新，无此问题）。没有这次复判，普通终端里的划词全部被误杀。
- **Electron 无障碍激活**：Chromium 系应用（VS Code、Claude Desktop 等 Electron 应用；Chrome 本体走插件不经此路径）的无障碍树默认关闭，焦点完全探不到。首次遇到这类应用时向其注入 Electron 官方开关 `AXManualAccessibility=true`（每应用实例只试一次），0.3 秒后复判。实测（本机 VS Code 1.130 / Electron 42、Claude Desktop）注入后 AX 树即可用，连注入前就存在的选区都能读到。非 Electron 应用会拒绝该属性，无副作用。
- **异步与过期丢弃**：证据探测不在事件回调/主线程做——AX 询问对假死应用最多阻塞 0.3 秒×2，而事件监听挂在主线程 run loop，拖住主线程就是拖住全局事件投递（前车之鉴：AX 超时收紧到 0.3 秒那次加固）。异步带来的过期结果用手势代数（随每次按下/按键递增）丢弃。

## Consequences

- AX 健康的应用（多数原生应用、激活后的 Electron 应用）假阳性全灭，且拖窗口时若焦点控件选区为空也能正确压掉；焦点控件还留着历史非空选区时拖窗口仍会浮图标——严格说「存在非空选区」符合期望行为，靠图标超时消失兜底。
- AX 暴露不全的应用（WhatsApp 这类 Catalyst/自绘 UI）回到修复前行为：图标能用，但该应用内的拖窗口/双击空白误报也一并回来——无证可判时宁可误浮，不可失能。
- 被注入激活开关的 Electron 应用会常驻启用无障碍树（应用内存/CPU 略增；个别应用如 VS Code 可能进入「检测到屏幕阅读器」模式）。这与 PopClip/Easydict 等同类工具的做法一致；开关随应用退出失效。
- 每次选取手势的成本：快路径 2 次 AX IPC（正常应用约 1ms）；假死应用最坏 0.6 秒且只拖慢图标浮现，不阻塞输入。每次左键按下多读一次剪贴板 changeCount（微秒级）。
- 剪贴板信号可能被无关写入干扰（手势期间恰有其他进程写剪贴板则误浮图标）——窗口极短，接受。
